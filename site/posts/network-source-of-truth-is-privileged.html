Your Network Source of Truth Is a Privileged System

JF
Jay French
Oct 29, 2026  ·  3 min read

I recently started as a Network Engineer at Salina Regional Health Center, and one habit I want to carry into the job is treating the systems that describe the network with the same care as the devices that run it. If your automation reads from NetBox or Nautobot, patch releases aren't boring. This post walks through three recent examples of why.

This is a general write-up based on public release notes. It isn't a description of any employer's systems.

A Source of Truth Is More Than a Database

A network source of truth starts life as documentation: sites, devices, circuits, prefixes. Once Ansible, CI checks, and config generation start reading from it, it becomes something else. It decides what gets built, what gets validated, and what gets pushed. That makes it a privileged system, and it deserves the upgrade and permission discipline you'd give a core router.

Three Releases Worth Reading

Nautobot 3.2.8 (Oct 27): a security release

Nautobot 3.2.8 fixes stored XSS in several places. It also fixes permission bugs where jobs and imports could reference objects the user wasn't allowed to view, and reveal that those objects existed. Neither is exotic, but both sit on a system many people can log in to and that many tools trust.

NetBox 4.7.4 (Oct 27): a breaking change in a patch release

The GraphQL enum for circuit status is now exposed as CircuitStatusEnum, and its values carry a STATUS_ prefix, consistent with the other status enums. A query that filters on {exact: ACTIVE} has to become {exact: STATUS_ACTIVE}. 

# Before 4.7.4
{exact: ACTIVE}

# After 4.7.4
{exact: STATUS_ACTIVE}

If you pull circuit status into reports or pipelines, that's a silent failure waiting to happen. Nothing crashes. A filter just stops matching what you expect, and the report looks fine until someone notices a circuit is missing.

NetBox 4.7.0 and 4.7.1: tokens in job results

Earlier in the 4.7 line, NetBox recorded plaintext API tokens created through background bulk requests in job results, where any user permitted to view jobs could read them. NetBox 4.7.2 fixed it by rejecting such requests, and the release notes say any tokens created that way should be considered exposed and replaced.

Replace the tokens, not just the version. Upgrading to 4.7.2 or later stops new tokens from leaking, but it doesn't un-expose tokens that were already recorded.

What I'd Do About It

  • Read the release notes before every upgrade, patch releases included. The circuit status change shipped in a patch release.
  • Run your GraphQL queries and Ansible inventory against a staging instance first. Silent filter changes are easier to catch there than in a production report.
  • Scope API tokens tightly and review who can run jobs. Job results and job lists are exactly where the token exposure and the Nautobot permission bugs showed up.

The source of truth drives your automation. Upgrade and permission it like a core router.

Takeaway

The more of your network that is generated, validated, and deployed from a single system, the more that system matters. Patch it on a schedule, test the integrations that depend on it, and give it the least privilege that still lets the automation work.

Sources: the Nautobot v3.2.8 release notes and the NetBox v4.7 release notes.
